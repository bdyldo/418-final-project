==================================

--------
Command profiled:
  env OMP_NUM_THREADS=64 OMP_PROC_BIND=true OMP_PLACES=cores \

Main interpretation
-------------------
1. The strongest signal is not low IPC. IPC is actually high at 2.54. The
   bigger problem is the enormous kernel-side memory cost:
   - 40.2 million page faults
   - 379.2 seconds of system time
   - less than 1 CPU utilized on average

2. For wide_1024, robot-level bitset parallelism is active. In the benchmark
   harness, bitset switches to outer robot parallelism when:
     robot_count >= 4 * rows
   Here that is:
     1024 >= 4 * 128
   so the N=64 run executes many independent robot searches concurrently.

3. Each robot search allocates large dense structures:
   - buildConstraintIndex() is called twice per search
   - each ConstraintIndex contains 5 dense bitset arrays over
     (horizon + 1) * rows * chunk_count words
   - parent_move stores one byte per (time, row, col)

4. That means the wide_1024 N=64 run is not compute-bound first. It becomes
   memory-allocation / page-zeroing / paging-pressure bound. The perf data
   matches this exactly:
   - very high page-fault count
   - system time far larger than user time
   - backend stalls much larger than frontend stalls

5. This explains why scaling improves nicely up to N=32 in the batch run, then
   flattens and bumps upward at N=64. By that point, adding more concurrent
   robot searches mostly increases pressure on memory bandwidth and the kernel's
   page management rather than increasing useful compute throughput.


Code evidence
-------------
Robot-level parallelism in the benchmark harness:
  benchmarks/benchmark_runner.cpp
  - outer threshold: lines 199-201
  - outer OpenMP loop: lines 247-253

Double dense constraint-index build in bitset search:
  src/bitset_wavefront.cpp
  - preliminary and final index builds: lines 166-172

Dense per-search storage allocations:
  src/bitset_wavefront.cpp
  - current/next/masks/parent_move: lines 192-200
  - dense ConstraintIndex arrays: lines 367-373


Why N=64 regressed
------------------
The N=64 slowdown is best explained by crossing a memory-pressure threshold:
more robot searches are in flight at once, so more dense per-search arrays are
being allocated and touched concurrently. Once that happens, the run stops
scaling on compute and starts paying heavily for page faults, zero-fill, kernel
memory work, and shared-memory bandwidth contention.

The fact that the batch N=128 run recovered somewhat relative to N=64 suggests
that the exact N=64 bump is partly node/run noise. The broader conclusion is
still the same: the curve starts saturating after N=32 because memory-system
pressure dominates.


Best next improvements
----------------------
1. Add a no-constraints fast path for bitset benchmarks so empty-constraint
   runs skip both dense buildConstraintIndex() calls entirely.

2. Avoid keeping both the preliminary and final dense ConstraintIndex objects
   live at the same time, or switch to iterative horizon growth instead of
   "build twice."

3. Reuse or pool per-search storage per worker thread instead of allocating
   fresh large arrays for every robot search.

4. Cap outer robot parallelism for wide_1024 below the point where memory
   pressure dominates, likely closer to 32 than 64 on this workload.
