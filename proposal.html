SUMMARY

We are going to implement and evaluate several concurrent queue designs for a trading-style market data processing pipeline on a multi-core CPU platform. Our main focus is a bounded lock-free Multiple Processor Multiple Consumer (MPMC) ring buffer, which we will compare against mutex-based, SPSC, and lock-based MPMC baselines using throughput, latency, and scalability measurements under multiple types of realistic producer-consumer workloads.

BACKGROUND

In modern electronic trading systems, a common systems problem is moving large volumes of market data from feed handlers to downstream processing stages with very low latency. Incoming updates may include simulated price ticks or order book deltas, and these messages must be transferred quickly from producer threads to consumer threads that update in-memory state or compute lightweight statistics. Since these systems operate at high message rates and may experience bursts during market open or major news events, the communication structure between stages can become a performance bottleneck.

Our project studies this problem through the design and evaluation of bounded queue implementations embedded inside a realistic application. Rather than benchmarking a queue in isolation, we will place the queue inside a synthetic market data ingestion pipeline: 

[Feed Handler Threads]  --->  [Queue]  --->  [Processing Threads]

Producers generate synthetic updates according to configurable arrival models such as uniform-rate traffic, Poisson arrivals, and bursty spike-based workloads. Consumers read these updates and perform small units of work, such as updating an in-memory book representation or computing aggregate statistics. This setting exposes queue behavior under different traffic patterns, contention levels, queue capacities, and consumer work sizes.

Parallelism is naturally present in this workload. Multiple producer threads can concurrently inject messages into the system, and multiple consumer threads can process messages in parallel once they are safely published. Because the queue lies directly on the communication path between these stages, its design strongly affects end-to-end throughput, tail latency, and scalability. This makes the problem a good fit for studying parallel systems behavior on multi-core CPUs.

THE CHALLENGE

The main challenge is that MPMC queues are much harder to implement and optimize than simple single-producer/single-consumer queues. A lock-free design must ensure correctness under concurrent access while also keeping synchronization overhead low enough to outperform lock-based alternatives.

The workload has several characteristics that make this difficult. First, producers and consumers communicate through a shared bounded buffer, so there is substantial synchronization and communication relative to the amount of computation performed per message, especially when consumer work is small. Second, the queue metadata (especially head and tail positions) may become hotspots, creating heavy contention on atomic read-modify-write operations such as fetch_add. Third, correctness depends on carefully ordered publication and reuse of slots, since consumers must not observe a slot before its payload is fully written, and producers must not overwrite unread data.

The memory access pattern has both favorable and unfavorable aspects. Ring buffers have good spatial locality because storage is preallocated in a contiguous array, but repeated access to shared indices and per-slot sequence numbers can still create cache coherence traffic. False sharing is another concern if frequently updated variables reside on the same cache line. In addition, small queue sizes increase wraparound pressure and intensify reuse of the same slots, which can worsen contention and tail latency under bursty workloads.

From a systems perspective, one major difficulty is mapping a highly synchronized workload efficiently to a multi-core CPU. We expect challenges involving memory ordering, store visibility, cache invalidation, and the cost of atomic operations. We also want to learn when a lock-free design actually helps, when contention causes it to degrade, and how application-level workload properties influence that crossover.

RESOURCES

We plan to implement the project in C++ using the C++ standard library's atomic and threading support on GHC and PSC machines available to us for development and benchmarking. We are starting from scratch rather than using an existing concurrent queue codebase, since a major goal of the project is to understand and implement the synchronization logic ourselves.

Our baseline implementations will include:

  • a mutex-protected queue using std::queue and std::mutex,
  • a simple SPSC ring buffer,
  • a lock-based MPMC queue, and
  • a bounded lock-free MPMC ring buffer using per-slot sequence numbers.

We will use course material on synchronization, memory ordering, and performance analysis as a reference, along with standard documentation for C++ atomics and any relevant papers or writeups on bounded MPMC ring buffers that we consult during implementation. At the moment, we do not anticipate needing special hardware beyond access to a reasonably modern multi-core machine for controlled experiments.

GOALS AND DELIVERABLES

Plan to Achieve

  • Implement four queue designs: mutex-based queue, SPSC ring buffer, lock-based MPMC queue, and bounded lock-free MPMC ring buffer.
  • Build a market data pipeline benchmark harness with configurable producers, consumers, queue sizes, message sizes, and arrival patterns.
  • Evaluate performance under different thread configurations, including 1P-1C, few-producer/many-consumer, many-producer/few-consumer, and many-to-many stress cases.
  • Measure throughput, average latency, and tail latency (at least p95 and p99).
  • Study how contention level, queue size, and per-message work affect relative performance of the implementations.

A successful project for us means producing a working lock-free MPMC queue, embedding it in the application pipeline, and carrying out a thoughtful experimental evaluation that explains the performance tradeoffs rather than only presenting raw timing numbers.

Hope to Achieve

  • Measure additional hardware-level effects such as cache miss behavior, false sharing, or time spent spinning under contention.
  • Extend the benchmark into a multi-stage pipeline, such as Stage 1 → queue → Stage 2 → queue → Stage 3, to study backpressure propagation.
  • Explore optimizations to reduce atomic contention or improve cache behavior, then quantify their effect.

Fallback if Progress Is Slower

  • If the fully lock-free MPMC implementation takes longer than expected, we will still complete the application harness and evaluate the mutex, SPSC, and lock-based MPMC baselines thoroughly.
  • If advanced hardware-counter analysis is too time-consuming, we will prioritize a strong experimental study using throughput, latency, scalability, and contention trends.

Questions We Hope to Answer

  • When does lock-free outperform mutex-based synchronization?
  • When does MPMC performance stop scaling as threads increase?
  • How much do bursty arrivals hurt tail latency and drop rate?
  • How much does queue size affect contention and wraparound pressure?
  • When does queue overhead dominate total runtime versus when consumer work dominates?

Demo

If time permits, we may show a live benchmark demo that visualizes message rate, queue occupancy, throughput, and latency under different workload modes. However, our primary focus is on a strong experimental evaluation rather than a live demo.

PLATFORM CHOICE

A multi-core CPU platform like GHC and PSC machines are natural fit for this workload because the application consists of multiple communicating threads that execute concurrently and share memory. The primary issues we want to study—atomic synchronization, cache coherence, false sharing, memory ordering, and contention—are all central CPU-side parallel systems issues. Using C++ also makes sense because it gives us direct access to low-level concurrency primitives and memory-ordering control while still allowing us to build a reasonably clean benchmarking framework.

This platform is especially appropriate because our project is not simply about raw computation throughput; it is about the interaction between application behavior and synchronization mechanisms. A multi-core shared-memory machine exposes exactly the kinds of bottlenecks that bounded concurrent queues encounter in practice.
